# tune-flow — 持續優化作業流程(操作手冊)

把「一個月跑一次的流程健檢」固化成可重複的迴圈。這不是「自動改你的設定」,是
**用三方對立視角找出真痛點 + 用紀律擋掉過度工程 + 把決策記下來不重蹈**。

## 核心原則(不可妥協)

1. **人決定「做不做」;skill 只負責「找出該做什麼 + 證明做得對」。** 中間**必停下等 使用者勾選**,絕不一路自跑到底就動手改設定。
2. **每個「要做」必須附三樣**:用什麼機制(hook/skill/SKILL 改)、測試怎麼跑、**逃生門是什麼**。湊不出逃生門 = 這個守衛不該存在。
3. **沒量化證據不准提常駐自動化。** 「沒人盯的自動化 = 默默壞掉沒人知道 + 一直燒資源」。要提常駐/背景服務,先證明它「壞了會大聲喊」+「你 能一鍵關掉接管」。
4. **決策要記、不重蹈。** 「不做」的記原因、「緩」的記重啟條件,下次同一個爛點子不會又被提一遍。

---

## 迴圈:5 步 + 3 個決策閘門

### 步 0 — 找訊號源（先盤點你環境裡真的有什麼）

訊號源因環境而異——**每一項都先實際確認存在再用，不要假設有**。按可信度排：

1. **機制自己的 log**（最硬，如果有）：如果這個環境裝過自訂 hook 或守衛，
   它們的 audit log 能查出誤報率；沒 log 的機制只能靠讀 code 推論。
   **剛裝好的環境通常一個都沒有——沒有就跳過，不是錯。**
2. **工作筆記裡「踩過的雷」**（如果使用者有記 session／專案筆記的習慣）：那裡是真的發生過的摩擦。
3. **使用者口述的痛點**——**永遠可用，而且常比任何報告準**。
   前兩項都空的時候（新環境很正常），這一步就是直接訪談：
   「最近哪件事讓你重做最多次／等最久／最火大？」問出 3-5 條就夠開工。

報告開頭要寫明「這次用了哪些訊號源」。跨多台機器工作的人注意：
log 與筆記只涵蓋它所在那台機器，在副機跑只看得到副機那部分。

### 步 1 — 抓摩擦訊號

從報告抽出:friction 分類 + 次數、what-works、suggestions、on-the-horizon。
**加上 你 口述的痛點**(常比報告準)。整理成一張「候選優化點」清單餵給辯論。

### 步 2 — 派三方辯論(可重複的核心)

派 **3 個並行 agent**(`general-purpose`),把候選清單 + 相關背景餵進去,各帶**固定職責**:

- **代表 你**:站他真實作業立場,按**爆炸半徑**(不是次數)排哪個最痛;報告建議哪些不切實際/會拖慢他。預設反駁:Skill 專家想把一切自動化、抓錯派會質疑優先序。
- **Skill 專家**:從既有 skill 生態找最高槓桿的優化(能不能 hook/skill 化、現有 skill 能不能強化合併)。**每個提案附「成本 vs 真實收益」一句**,並明講哪些「其實不該做」。自律:你 討厭為 skill 而 skill、討厭殘廢 stub、討厭過度工程拖慢。
- **抓錯派(red team)**:不提方案,專挑盲點。**固定鐵律**(每次都要打):
  1. **質疑數字**:friction 次數是不是 LLM 事後自評貼的?有沒有把「健康的來回迭代」誤標成 friction?分母多少?
  2. **頻率 ≠ 嚴重度**:高次數可能只是 你 自己吞時間;按可逆性/爆炸半徑排。
  3. **守衛要配逃生門**:任何「先確認/先擋」建議,沒設計「你 怎麼快速通過」就是換一種摩擦。
  4. **常駐自動化是 silent-fail 溫床**:24/7 守護、背景 swarm —— 沒「壞了會喊 + 一鍵關掉」就擋下。
  5. **沒證據別硬塞**:解決方案找問題 = 強塞;要量化證明「目標問題真的存在」。

**辯論 agent 輸出紀律**:報告全文寫到 scratchpad 檔案,回傳訊息只給「檔案路徑+短摘要」——長報告直接回訊息會撞 32k output token 上限(2026-07-12 量化:全窗爆 token 6 次全是這類長報告 agent,主對話 0 次)。

> 背後的原則:大動作前先驗證假設;別的地方沒有同樣問題就不要推同一套解法;不做殘廢 stub。

### 步 3 — 收斂成清單 →【決策閘門 A】

主 Claude 整合三方,產出一張表:

| 項目 | 分類 | 機制 | 測試 | 逃生門 | 證據強度 |
|------|------|------|------|--------|---------|
| … | 做/緩/不做 | hook / skill / SKILL 改 / 不適用 | 怎麼驗 | 怎麼快速通過 | 跑過幾次 / 量化 |

**🛑 決策閘門 A —— 停。把清單交出去,等使用者勾選「哪些真的要做」。**
- 不勾 = 不做。你 可以改分類、改範圍、加自己的點。
- **絕不自己決定就跳去動手**(這違反核心原則 1)。

### 步 4 — 動手(只做 使用者勾的)→【決策閘門 B + C】

對每個勾選的項目:

**🛑 決策閘門 B(動手前)** —— 先列「要新增/改哪幾個檔」等使用者點頭(防呆規則:動設定/多檔修改前先講計畫)。然後:
- 寫程式:小檔、immutable、**完整功能不留 stub**、UI 繁中、有逃生門。
- **寫測試 + 自己跑綠**(正反案例都要)。hook 類做回歸測試檔。
- 做完**自我驗證**:端到端跑一次(不只測零件)。

**🛑 決策閘門 C(同步/不可逆)** —— push / merge / 跨機器散佈:
- 設定有跨機同步機制的就走它(讓各機器自己拉,**不要手動 SSH 去各機器 pull**);沒有就只改本機。
- push 到 main、改正式環境等不可逆動作 → **要使用者具名授權**(不是「好」)。
  如果環境裝了擋不可逆動作的防護 hook,照它的放行規則走,理由照使用者的話填、別自編。

### 步 4.5 — 新機制的完工定義(2026-08-26 加,第六次的教訓)

**新守衛/新 hook 上線的第一天就必須留痕;上線後 7 天內回頭看一次誤報率,看完才算完工。**

為什麼:08-21 一次上線五個機制,四天後回頭查——一個誤擋過半、兩個從沒被呼叫過、
一個幾乎零命中。**能查清楚的那一個,靠的就是它有 log**;另外兩支是靠工具名不匹配才碰巧抓到,
下次沒這麼好運。沒有留痕的守衛 = 你永遠不會知道它壞了。

配套三條(缺一不可):
- **有 log**:至少記「命中哪條規則 + 指令前 80 字」。**不要記全文**——log 是明文檔,
  被擋的指令裡可能有 `grep .env.local`,別把稽核變成新的洩漏面。
- **有測試檔留在目錄裡**。「我當場跑過 9 個案例都過」不算——上一輪就是這樣說的,
  結果目錄裡一個測試都沒有,壞了四天沒人知道。**測資要用真實紀錄,不要用自己捏的 payload**:
  08-21 五項全都通過了自己寫的測試,四天後三項是壞的,差別就在餵進去的不是系統真正送出的那份。
- **有下架條件寫在檔頭**:例如「兩週後誤擋率仍 >20% 就下架,不修第三次」。

### 步 5 — 記決策(持續優化的命根子)

把這次結果寫進一份**放在使用者自己目錄的**決策紀錄檔(建議 `~/.claude/tune-flow-decisions.md`,
第一次跑先建立)。**不要寫進 plugin 安裝目錄**——plugin 更新時整個目錄會被換掉,紀錄會消失。內容:
- **做了的**:項目 + 日期 + 在哪(檔/commit)。
- **緩的**:記**重啟條件**(「下次碰 POS 時」「若連線天天壞」)——條件到了下次跑會自動浮出來提醒。
- **不做的**:記**原因 + 重評條件**——同一個爛點子下次不會又被當新建議提一遍。

每次跑 tune-flow 開頭都先讀這份,避免重蹈/重議。

## 絕對不要做

- ❌ 一路自跑到底就改 你 的設定(沒過決策閘門 A)。
- ❌ 把「辯論」做成 AI 自己同意自己(三方要真對立,抓錯派一定要打數字與常駐風險)。
- ❌ 提常駐/背景自動化卻沒設計「壞了會喊 + 一鍵關掉」。
- ❌ 做殘廢 stub / 「Coming soon」。
- ❌ 手動 SSH 去各機器 pull 設定(靠 auto-sync)。
- ❌ 決策不留紀錄(下次又從零想、爛點子又被提)。
