# mockup-demo — 先做得出來被罵，再做得出來上線

## 為什麼有這支

這半年的實際軌跡：一個訂單系統的 mockup 疊代到 **v7.1**、一套後台 UI 疊代到 **v9**、
一份客戶提案改了四輪。**每一輪都不是程式寫錯，是畫面沒對齊。**

而對齊的方法其實已經很穩定，只是沒寫下來——這支就是把它固定下來：

1. **他要的不是一個 mockup，是 2-3 個並排讓他挑。**
   實例：「分享管理 UIUX 優化？」→ 三個 mockup（Drive 彈窗／卡內分頁／右側抽屜）→ 拍板案一 → merge。
   「UI 要做文件分類」→ 三個 mockup → 拍板 B+C。**只端一個方案上去，等於替他做了決定。**
2. **他會改變心意，所以舊版不能刪。**
   實例：「看完新 mockup UI 反而覺得舊的比較好」。版本要能並排比較。
3. **定稿那份就是規格書。**
   實例：拿定稿 mockup 逐欄比對，抓到列表缺「業務」「逾期天數」兩欄。
   **不做這一步，缺欄位會在上線後才被發現。**

---

## 步 0 — 先問三題（決定這份要做成什麼樣）

不要直接開始畫。先確定：

| 問題 | 影響什麼 |
|---|---|
| **給誰看？** 決策者挑方案／客戶窗口／客戶老闆 | 決定發哪裡、要不要導覽、能不能有技術味 |
| **要挑什麼？** 版面配置／互動流程／文案 | 決定要做幾個方案、差異放在哪 |
| **哪一頁是講不清楚的那一頁？** | **只做那一頁**。其他頁空殼就好 |

然後**複述一句**再動手：「我理解你要的是 X，我做 A/B/C 三個方向讓你挑，對嗎？」
（範圍／視覺／創作類一律停下等確認；純技術細節自己決定。）

---

## 步 1 — 做 2-3 個方案，不是一個

**除非他明確指定做法，否則預設端 2-3 個方向並排。**

- 每個方案要**只差在一件事**上（版面／互動／資訊密度擇一），差太多就沒得比。
- 三個方案放**同一頁**，用分頁或並排；他要能來回切換。
- 每個方案下面寫一行「這個方案的代價是什麼」——沒有代價的方案是假的。

## 步 2 — 假資料要假得像真的、而且能操作

拍板過的標準：**「互動＋流程圖＋假資料可操作」**。

- `測試1 / 測試2` 他看不出問題。放**他業務裡真的會出現**的名字、金額、日期、狀態，
  他才會說「這兩個狀態不會同時出現」——**那句話就是這份 mockup 的全部價值**。
- 但**不要用真的客戶個資**（像真的 ≠ 是真的）。
- 主要動作要真的會有反應（按了會變、會跳、會加一列），不要整頁死的。

## 步 3 — 單檔、全內聯

- **一個 `index.html`，樣式與腳本全內聯**，不要外部檔。
  原因：任何分享管道對外部資源、檔案數、副檔名都有限制，單檔最不會卡。
- **檔名與資料夾名不能有空格**（多數靜態託管會拒收）。
- 檔名帶主題與日期：`<主題>-mockup-<YYYYMMDD>.html`。
- **先寫在暫存區，再走發佈流程**——不要直接寫進發佈工具的目的地資料夾，
  很多發佈腳本會因為「來源＝目的地」而中止，結果檔案在、清單上卻找不到。

## 步 4 — 真瀏覽器驗過才給他看

**不要把沒開過的頁面丟給他。** 用 Playwright 至少驗這四項：

- 主要互動真的會動（點了有反應、加得了列、送得出去）
- **390 / 768 / 1024 / 1440 四個寬度零橫向溢出**（他常在 iPad 看）
- 零 console error
- 空值／極端值不破版

（實例：訂單分配中心 v7.1 驗了 16 項才發佈；抓過 768 寬度 44px 溢出。）

## 步 5 — 給人看：預設本機直接開，要傳出去才發佈

**預設做法不需要任何帳號、額度或發佈管道：檔案存在本機，直接用瀏覽器開給他看。**
當面、投影、螢幕分享都走這條；對方不在場也可以直接把那個 HTML 檔傳給他——
步 3 堅持單檔全內聯的好處就是**傳檔即可用，點兩下就開**。

**只有「對方不在旁邊、又要能自己反覆點」才需要發佈成網址。**這時**先問使用者手上有什麼管道**
（公司內部檔案伺服器、靜態託管、自架站……都行）——不要假設他有現成的，
也不要替他挑一個要註冊帳號或花錢的服務。

真的要發佈時，看給誰看分兩條路：

| | 給自己人挑方案 | 給客戶／外部窗口看 |
|---|---|---|
| 需要什麼 | 一個能傳的網址就好 | **要登入才看得到**、能指名分享 |
| 發佈前 | 自己決定 | **一定要先取得同意**——連結出去就收不回 |
| 內容 | 可以有技術味、可以三案並排 | 不放技術用語、不放價格、要有導覽感 |

**兩條路共同的鐵律：同一份 mockup 重發要回到同一個網址。**
每改一版換一個連結，對方會分不清哪個是最新的，而且舊連結還活著會造成誤會。
（自架站＝同檔名覆蓋；多數託管平台＝重發時帶上該頁的識別碼。**漏帶就會開出新頁面。**）

改完之後回覆對方時，**網址後面加 `?v=2` 之類的參數**——否則他的瀏覽器會給他舊版，
他會以為你根本沒改。

## 步 6 — 定稿之後：把它變成驗收清單

**這一步最容易被跳過，而它是這支最值錢的地方。**

拍板之後，把定稿 mockup **逐欄逐區塊列成清單**，實作完成後拿它一項一項比對。
（實例：靠這一步抓到列表缺「業務」「逾期天數」兩欄——不做就會上線後才發現。）

清單寫進工單或 session note，不要只存在腦子裡。

## 版本紀律

- **舊版不刪。** 檔名帶版號或日期，他會回頭要「上一版比較好」。
- **同一份 mockup 重發要回到同一個網址**（自架站同檔名覆蓋／託管平台帶該頁識別碼）——
  每改一版換一個連結，對方會分不清哪個是最新的。
- 迭代到 v4 以上時，在頁面上標版本與日期，否則兩邊會在講不同版。

## 給客戶窗口的額外要求

被退過一次：**「demo 給窗口太複雜；每區塊要能一步一步操作、連結前後來回」**。

- 窗口版要有**導覽感**：一步一步、每步只做一件事、可以回上一步。
- 頁面上明講「這是原型，資料是假的、部分按鈕沒有反應」——一行字省掉一場誤會。
- 不要放技術用語、不要放價格（提案簡報的價格頁另案，見 `pitch-deck`）。

## 收尾：原型一定要有下場

三選一，**不要留無主的殭屍連結**：

1. **要做成真的** → 走步 6 產出驗收清單，接實作流程；若分享平台支援「申請上線」就讓客戶自己按（會直接變成工單）。
2. **不做了** → 有發佈的就下架，並把「為什麼不做」記進工作筆記——否則半年後有人重提同一個點子。
3. **還在等** → 寫下**在等誰的什麼回覆**。

## 踩過的雷

- **一次做太多頁** → 先做「大家講不清楚的那一頁」，其他空殼。
- **只端一個方案** → 等於替他做決定，他會要你重做。
- **改完忘了給 `?v=N`** → 他看到舊版，以為你沒改。
- **重發時漏帶該頁識別碼** → 開了新頁，窗口手上的連結還是舊的。
- **頁內有兩顆同名按鈕**（例如兩個「收單」）→ 測試選擇器要用 `onclick` 屬性挑，別用文字。
- **原型太像成品** → 客戶以為快好了，開始問上線日期。

## 相關

- **發佈管道由使用者的環境決定——先問，不假設**；預設本機開檔就夠（見步 5）
- 定稿後的實作迴圈：你自己的開發流程 skill
- 提案簡報（含不放價格的紀律）：`pitch-deck`
- 產出 HTML 交付物的共用機制：`html-note`
